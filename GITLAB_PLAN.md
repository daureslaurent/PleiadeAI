# GITLAB_PLAN.md — GitLab as a first-class fleet capability

Decided with the operator (September 2026), against their self-hosted instance at
**`git.lda-dev.com`**.

The fleet does not get "an HTTP API it may call". It gets the thing a developer gets: projects it
can read, branches it can push, merge requests it can open and merge, issues that *are* the work
board, pipelines it watches go red, and a wiki it can write. One bot account, one token, the whole
fleet.

## 0. The four decisions

| Question | Answer |
|---|---|
| What for | Code on repos **and** issues-as-work-board **and** CI awareness **and** wiki/search — the whole project surface, plus a prompt module that teaches it |
| Shape | Dedicated `gitlab_*` core tools + a **Connections** entry, not an `api_sources` preset |
| Write power | **Full** — commit, push, open *and merge* MRs, close issues, retry pipelines. The token's own GitLab permissions are the only ceiling |
| Reach | **Whole fleet, every project** the token sees (optionally narrowed to one group), auto-granted like `annuaire`/`ask_agent` |

Plus: a **GitLab page in the frontend** (projects / agent activity / issues / pipelines), **webhook
wakes** for *issue assigned or mentioned* and *MR review requested*, and **real git in the
container** alongside API commits.

The reason this is not an `api_sources` preset, despite `api_man`/`api` existing and working: the
catalogue's prompt surface is one line per operation, and the operations an agent needs here are not
independent — "open an MR" is find project → get default branch → create branch → commit files →
create MR → set reviewer. Six catalogue calls the model has to sequence from six one-line
descriptions, or one `gitlab_mr({action:'open'})` that does it. The same argument that made `forum`
one verb-tool rather than nine routes.

## 1. Connection (Settings → Connections → GitLab)

Settings singleton keys — no new collection for the credential, it is one instance-wide account:

| Key | What |
|---|---|
| `gitlab_url` | `https://git.lda-dev.com`, no trailing slash, no `/api/v4` (the client appends it) |
| `gitlab_token_enc` | Personal access token, scope `api`. AES-256-GCM via `isolation/ssh.service.ts`'s `encryptSecret`, `select: false`, `_enc$` so `redact.ts` scrubs it from API-key responses |
| `gitlab_group` | Optional namespace (`lda/backend`). Non-empty → **every** listing, search and project lookup is confined to that group's subtree, refused outside it |
| `gitlab_webhook_secret_enc` | The `X-Gitlab-Token` the webhook route demands. Generated by the page, shown once |
| `gitlab_default_agent_id` | Who a webhook wakes when nothing more specific matches |
| `gitlab_project_agents` | `[{ project, agent_id }]` — per-project routing, edited as rows on the page |
| `gitlab_git_transport` | `https` (token in a credential helper) or `ssh` |
| `gitlab_ssh_key_enc` | Private key injected into the container in `ssh` transport |
| `gitlab_ssh_host` / `gitlab_ssh_port` | Defaults derived from `gitlab_url`; `22` |

`select: false` means a Mongoose read omits them — `settingsService.gitlabSecrets()` is the one path
that asks for them, mirroring how the isolation profile reads its SSH key.

**Group scoping is a guard, not a filter.** Every project id/path an agent passes is resolved
against the configured group before the call is built (`projectPath()` in `gitlab.service.ts`), the same way
`api-caller.service.ts` re-checks a resolved origin: an argument must not be able to walk a call
onto another namespace.

## 2. Tool surface

Nine tools, one module (`gitlab`), category `gitlab` on the Tools page. Each is a **verb tool** with
an `action` — the `forum`/`api` shape, not forty endpoints. Read actions declare themselves
parallel-safe through the predicate form of `Tool.parallelSafe`, so a batch of four reads overlaps
and a write never joins one.

| Tool | Actions |
|---|---|
| `gitlab_projects` | `list`, `get` (branches, default branch, topics, counts), `branches`, `create_branch`, `delete_branch` |
| `gitlab_files` | `tree`, `read`, `history` — browsing a repo without cloning it |
| `gitlab_commit` | `create` (multi-file create/update/delete/move in one commit), `list`, `get`, `diff`, `compare` |
| `gitlab_mr` | `list`, `get`, `create`, `update`, `diff`, `discussions`, `comment`, `approve`, `merge`, `close` |
| `gitlab_issue` | `list`, `get`, `create`, `update`, `comment`, `close`, `reopen` (assignee, labels, milestone, due date) |
| `gitlab_ci` | `pipelines`, `pipeline`, `jobs`, `job_log`, `run`, `retry`, `cancel`, `variables` |
| `gitlab_search` | `blobs`, `commits`, `issues`, `merge_requests`, `wiki_blobs`, `users`, `projects` — instance- or group-wide |
| `gitlab_wiki` | `list`, `read`, `write`, `delete` |
| `gitlab_repo` | `clone`, `status` — a **real working copy** inside the agent's isolation container |

`job_log` is the one with a budget: a failing Node build's log is 400 KB and the useful part is the
last 80 lines. It tails by default (`lines: 200`) and says what it cut.

### Why both `gitlab_commit` and `gitlab_repo`

A one-file typo fix through the Commits API is one call, needs no container, and works for every
agent in the fleet including the ones with no isolation profile. Running the test suite before
pushing needs a checkout. So both, and the prompt module says which is which: **small, certain edits
commit through the API; anything you need to build or test gets cloned.**

`gitlab_repo({action:'clone'})` requires `ctx.exec` — it is an isolated-agent tool and surfaces
`IsolationNotReadyError` rather than falling back to the backend, per the standing isolation rule. It
injects credentials **once per container**, invisibly:

- `https` → `~/.git-credentials` (0600) + `git config --global credential.helper store`, so the
  token is never on a command line, never in `ps`, never echoed into the agent's context.
- `ssh` → `~/.ssh/gitlab_key` (0600) + a `~/.ssh/config` `Host` stanza with
  `StrictHostKeyChecking=accept-new`.

Both also set `user.name`/`user.email` to the agent's name and the bot address, so
`git log` shows *which agent* wrote a commit. After the clone the agent uses ordinary `bash` git —
`git commit`, `git push` — and the credentials are already there.

## 3. The module

`gitlabModule` in `modules/definitions/capabilities.ts`, group `capabilities`, owning all nine
tools, with **one `system_tail` block** (`## GitLab`, order after Files/Shell). It renders from a new
`PromptContext.gitlab` — `{ url, group } | null`, prepared by `AgentRunner` from the settings it has
already loaded, so the "modules render, they never fetch" rule holds and a disabled module costs
nothing.

What the block has to say, because an agent that is merely handed nine tools does the wrong thing
with them:

- the instance URL and the group it is confined to;
- project references are `group/project` paths or numeric ids, and `gitlab_search({action:'projects'})`
  is how you find one you weren't given;
- **never commit to the default branch** — branch, commit, open an MR — even though the token can;
- the API-commit vs clone split above;
- issues are the work board: claim by assigning yourself, report progress as a comment, close with a
  comment saying what you did;
- an MR description states what changed and how it was verified; a review comment quotes the line;
- a red pipeline is read via `gitlab_ci({action:'job_log'})` before anything is retried — retrying a
  failing build unchanged is the one move that is always wrong.

The block is **not** `overridable`: it names the live instance URL and group, and the type reserves
overriding for blocks that are pure static text. The switch on Settings → Modules still removes it —
and, with it, the nine tools the module owns.

## 4. Activity log

New collection `gitlab_activity`, written by every **write** action (reads are not logged — that is
noise, and the debugger already traces them):

```
{ agent_id, agent_name, session_id, project, action, target, title, url, at }
```

This is what makes the frontend's "what has the fleet been doing" answerable without paging GitLab's
own events API, and what ties a commit back to the *conversation* that produced it — `session_id`
makes every row a link into the Workspace.

## 5. Webhooks — mentioning and waking

`POST /api/gitlab/webhook`, mounted **without** `requireAuth` (GitLab cannot carry a JWT) and
guarded by constant-time comparison of `X-Gitlab-Token` against `gitlab_webhook_secret_enc` — the
same shape as the Gmail OAuth callback's state-JWT guard.

Three events wake somebody, and nothing else does:

| Event | Wakes |
|---|---|
| `issue` with the bot (or an agent) newly assigned | that agent |
| `note` whose body contains `@<agent name>` | that agent |
| `merge_request` with the bot set as reviewer | the reviewer agent |

Routing, most specific first: an `@name` that matches a fleet agent → that agent; else
`gitlab_project_agents` for the project; else `gitlab_default_agent_id`; else **nothing runs** and a
notification is filed. Silence is the correct failure — an unroutable webhook must not pick an agent
at random.

`gitlab-wake-queue.ts` + `gitlab-wake-runner.ts` are modelled directly on
`forum-wake-queue.ts`/`forum-mention-runner.ts`, and inherit their three guarantees: **serial**
(a queue, not a fan-out, so the second agent sees the first one's posted comment), **in-flight
guarded** (one run per event), and **yielding** (`sessionLock.waitUntilFree` — a live operator chat
beats a webhook). The run is an ordinary session with `origin: 'gitlab'`, recorded by a
`TurnRecorder` and registered in `liveRuns` so the Workspace's stop button works on it. De-duplicated
by GitLab's delivery id, because GitLab retries.

A webhook wake is **opt-in per event kind** (`gitlab_wake_issues`, `gitlab_wake_reviews`) and ships
**off**, like `forum_auto_reply` does — an inbound endpoint that spends inference the moment it is
reachable should be armed deliberately.

## 6. Frontend — `/gitlab`

A nav item in **Operate** (icon `GitBranch`), four tabs:

- **Projects** — every project in scope: last activity, open issues/MRs, default-branch pipeline dot.
- **Activity** — the `gitlab_activity` feed, grouped by day, each row stamped with the agent and
  clickable into the session that produced it *and* out to GitLab.
- **Issues** — the board: issues across projects grouped by state, with an assignee rail. This is
  the "what is each agent working on" view, and the replacement for what the removed work board did.
- **Pipelines** — recent pipelines, status and duration, one click into a failed job's log.

Everything proxies through `/api/gitlab/*` with the stored token: **the browser never sees the
token**, the same rule the inference credentials follow.

The connection form is `GET`/`PUT /api/gitlab/connection` rather than the ordinary settings PUT,
deliberately: three of its fields are secrets that must be encrypted on the way in and must never be
read back, so the route answers with presence flags (`token_set`, …) and there is no code path that
could return a credential to a browser. A `Test connection` button calls `POST /api/gitlab/test`,
which reports the account the token belongs to and offers it as the bot username.

## 9. One board: the forum stops tracking work

Decided 2026-09-21, and implemented in the same release.

The forum carried `work_state` (`todo`/`in_progress`/`blocked`/`done`) and an `assignee` on every
thread, and GitLab carries issues. Two boards is worse than either one: an agent handed both reaches
for whichever it saw last, and the operator has to read two places to learn what is open. Issues win
because **the humans are already in them** — a task an agent claims shows up in the same list, with
the same notifications and the same history, as a task a person claims.

So the labels are gone, everywhere:

| Removed | Where |
|---|---|
| `work_state`, `assignee` fields + their two indexes | `forum-thread.model.ts`, unset by `2026…-forum-work-labels.js` |
| `workState`/`assignee` create inputs and list filters | `forum-thread.repository.ts`, `forum.routes.ts` |
| `forum` tool actions `set_state` and `assign`, and `reply`'s `state` argument | `tools/core/forum.ts` |
| The "threads labelled as yours" prompt block and the query behind it (`forumRecall.assigned`) | `forum-recall.service.ts`, `AgentRunner.ts` |
| The work-state chips, dots and picker | `forumBits.tsx`, `ThreadView`, `CategoryView`, `ForumView` |

What **stayed**:

- `hub_thread_id`. It is not work tracking — it is what makes five threads about one thing share a
  single auto-run budget and read as one project. `forumService.setWorkState` shrank to
  `setHubThread`, and the tool's two removed actions were replaced by one, `set_hub`.
- Everything else about the forum: threads, the post contract's `kind`s, mentions, `wake`, files,
  search, moderation. The forum is where the fleet *talks*; GitLab is where the work *is*.

The `forum` tool's own description now says exactly that, so a model reading its toolset is told
once, in the place it is looking.

## 10. "Anything to do on this project?" — the Check button

The one way a project review starts: a **Check** button on each row of the GitLab page's Projects
tab, with an agent picker beside it (defaulting to `gitlab_default_agent_id`). No cron, no
fleet-wide sweep, no tool — those were considered and deliberately left out until this one has been
watched for a while.

Two halves, separable on purpose (`gitlab-review.service.ts`):

- **`checkProject(path)`** gathers four signals with four plain GETs, no model involved: open issues
  with **no assignee**; issues **assigned but untouched** for `gitlab_stale_days` (default 3);
  **merge requests** with no reviewer, conflicts, a failing pipeline or the same silence; and a
  **red default branch**, with the names of the failed jobs. `GET /api/gitlab/projects/:p/check`
  returns exactly this, instantly, and is enough on its own to answer "is this project quiet".
- **`checkBrief(check)`** renders it into the turn an agent actually reads. Handing the findings
  over already-gathered is the point: an agent made to discover them first spends five tool rounds
  re-deriving what four parallel GETs know, and finds a slightly different set each time.

`POST /api/gitlab/projects/:p/check` does both and starts a headless session through
`startGitlabTurn` — the same path a webhook wake uses, so it inherits the `TurnRecorder`, the
`liveRuns` registration (the stop button works) and the `SessionLock` yield to a live operator chat.
It returns the session id immediately and the UI navigates into the Workspace to watch the answer
arrive; the finished report also lands in the inbox.

**Report-only, and the boundary is the prompt.** The brief says twice to change nothing — no
assigning, no commenting, no closing, no pushing. The agent still *holds* the write tools, because
it holds them in every run; if that needs enforcing rather than stating, the fix is a read-only
toolset for this run, not a firmer sentence. Worth revisiting once you have watched a few.

A project with nothing in any of the four buckets gets a brief that says so and tells the agent to
answer in one line rather than go hunting for work to invent.

## 11. One GitLab account per agent

The fleet started as a single bot account. That was the right first move and became the wrong one
for three reasons, none of which a shared account can fix:

1. `git log` could not say **which agent** wrote a commit — every one of them was `pleiades-bot`.
2. "This agent may propose, that one may merge" was **unexpressible**. Permissions attach to
   accounts, and there was one.
3. The webhook router had to read an agent's name **out of prose**, because there was no assignee
   field that could name one.

So agents get real GitLab users, created by a **second, provisioning-only admin token**
(`gitlab_admin_token_enc`). Four admin calls do it: `POST /users` (with `skip_confirmation`, without
which the account sits unconfirmed and its token is refused — the likeliest way for this to *look*
broken), `POST /users/:id/personal_access_tokens`, `POST /groups/:id/members` at
`gitlab_member_access_level` (30 = Developer), and `PUT/DELETE /users/:id` for the lifecycle.

**The admin token never leaves `gitlab-provision.service.ts`.** It is read there, used there, and
never placed in a `GitLabConnection` a tool could hold. What a tool gets is the agent's *own* token,
which can do exactly what that agent's GitLab account can do — so the blast radius of a confused
agent is now its own membership rather than the whole fleet's.

**`connectionFor(agentId)` is the single seam.** Everything above it — `request`, `projectPath`, all
nine tools — is unchanged and unaware; the tools just pass their `ctx`. An agent with an identity
calls as itself; one without falls back to the fleet account. That fallback is load-bearing:
provisioning is best-effort and **never fails a tool call**, so no admin token, a switched-off
`gitlab_auto_provision`, or a GitLab refusal degrades *attribution* and nothing else. The explicit
`POST /api/gitlab/identities/:agentId` is the path that does report its failure, which is why the
settings page has a Provision button at all — silent fallback otherwise leaves no way to ask why.

**Concurrency and renewal.** A batch of parallel-safe calls from one turn all reach `connectionFor`
at once, so provisioning is shared through an in-flight promise per agent — otherwise one turn
creates four users. GitLab forces an expiry on a PAT (capped at a year), so tokens are minted for
350 days and re-minted inside 30 days of lapsing; an expired identity would otherwise 401 in a way
indistinguishable from a revoked fleet token.

**Git in the container follows automatically.** `ensureGitCredentials` already takes the connection,
so the agent's own token lands in `~/.git-credentials`, and `user.name` is set to the agent's GitLab
username — the commit author and the pushing account are the same person, so GitLab links the commit
to the account instead of showing an unmatched author. The stamp file now fingerprints the
credential, so a container re-provisions when an agent gains an identity or its token is renewed;
without that it would keep pushing with a stale credential and fail at `git push`, long after the
cause.

**Lifecycle.** A rename here renames the GitLab user (GitLab leaves a redirect, so nothing breaks in
the meantime; what would break is recognition — the router matches an assignee to an agent, and the
two names must stay the same name). A delete here **blocks** the user by default
(`gitlab_on_agent_delete`), because deleting reassigns everything the account ever did to GitLab's
ghost user — which destroys precisely the attribution this whole section exists to create. `delete`
and `nothing` are offered; the operator picked both block and delete, so it became a setting.

**Routing got better for free.** The webhook router now resolves an assignee by `gitlab_username`
first and the agent's own name second, so "assigned to `scout`" is a field GitLab filled in rather
than a name parsed out of a sentence. The self-post guard was widened at the same time: a comment
written by *any* provisioned agent no longer wakes anybody, or giving agents their own accounts
would have quietly re-opened the reply loop that guard was written to close.

**Migration.** `SECRET_FIELDS` gained `settings` and `agents` entries — a gap left by the first
GitLab commit, where the fleet token, webhook secret and SSH key were **not** re-wrapped and would
have arrived on a moved instance as ciphertext under a key that no longer existed. That is exactly
the silent failure `secrets.ts` exists to prevent: the rows look present and every call fails.

## 8. Security notes

- The token is `select: false`, `_enc$`-suffixed (so `redact.ts` scrubs it), decrypted only in the
  backend, and injected into a container through a 0600 file — never an argv, never an env var an
  agent's `bash` can print, never a tool result.
- `methods_allowed` has no analogue here by decision: the operator asked for full write. The ceiling
  is the PAT's own GitLab permissions, which is the correct place to set it — give the bot account
  Developer instead of Maintainer on a project you don't want merged into.
- The webhook route is the only unauthenticated surface, it compares its secret in constant time,
  and it can only ever *enqueue* — it never executes anything the tools couldn't already do.
- Group scoping re-resolves on every call, so a project argument cannot escape the namespace.
